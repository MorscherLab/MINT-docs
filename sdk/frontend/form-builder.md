# FormBuilder

`FormBuilder` in SDK **@MINT_VERSION@** renders a control model built with `defineControlModel()`. Pass it as the one `:spec` prop. Use the same model and value object for forms, settings, and sidebars so every control edits the same state.

`enhancements` and `actions` (the submit and cancel bar) are part of the control model, not separate props.

## When to use FormBuilder vs. hand-rolled forms

| FormBuilder | Hand-rolled |
|-------------|-------------|
| Form structure is data — comes from a plugin's design schema or a config | Form structure is fixed and known at compile time |
| You need conditional fields ("if X then show Y") declaratively | Conditional logic is simple `v-if` |
| Field set varies per experiment type or per-tenant | Same form everywhere |
| Validation rules are declarative (required, min/max, regex) | Custom validation needs (e.g., async server-side checks per keystroke) |

Most experiment-design plugins use FormBuilder for their design view. Analysis plugins use it when they have parameter forms, settings panels, or a sidebar generated by `PluginWorkspaceView`.

## Quick start

```vue
<script setup lang="ts">
import { ref } from 'vue'
import { FormBuilder, defineControlModel } from '@morscherlab/mint-sdk'

const spec = defineControlModel({
  controls: {
    name: {
      type: 'text',
      label: 'Panel name',
      placeholder: 'e.g. Cisplatin dose-response',
      required: true,
    },
    category: {
      label: 'Category',
      options: [
        { value: 'tox', label: 'Toxicology' },
        { value: 'eff', label: 'Efficacy' },
      ],
      default: 'eff',
    },
    replicates: { type: 'number', label: 'Replicates', min: 1, max: 12, default: 3 },
  },
  actions: true,
})

const data = ref({})
</script>

<template>
  <FormBuilder v-model="data" :spec="spec" @submit="save" />
</template>
```

`data.value` updates as the user types. Validation errors are rendered inline. `actions: true` shows the submit and cancel bar; without `actions`, the bar is hidden. The `submit` event carries only the values of the visible fields.

## Control models

A control model is the one definition for the form, the settings modal, the sidebar, and the top-bar settings. The SDK infers field types and defaults from simple values where it can. String and number option arrays are accepted directly by `BaseSelect`, `BaseRadioGroup`, and `SegmentedControl`, so you do not need to expand every option into `{ value, label }` unless labels differ from values.

```ts
import { defineControlModel } from '@morscherlab/mint-sdk'

const workspaceModel = defineControlModel({
  views: {
    run: {
      label: 'Run',
      sections: {
        analysis: {
          label: 'Analysis',
          controls: {
            threshold: { type: 'number', default: 0.05, min: 0, max: 1 },
            method: { default: 'linear', options: ['linear', 'logistic'] },
            includeQc: { label: 'Include QC samples', default: true },
          },
        },
      },
    },
  },
  initialValues: { threshold: 0.1 },
  actions: { submitLabel: 'Run analysis', showCancel: false },
})
```

To drive a whole page from the model, pass it to `PluginWorkspaceView` as `spec.sidebar.controls`. The workspace generates the sidebar sections, their forms, and the view pills. It does not render a main form. Put the main form in the default slot of the workspace:

```vue
<PluginWorkspaceView
  v-model:values="values"
  :spec="definePluginWorkspaceView({ title: 'Analysis', sidebar: { title: 'Run controls', controls: workspaceModel } })"
>
  <FormBuilder v-model="values" :spec="workspaceModel" @submit="run" />
</PluginWorkspaceView>
```

Do not nest a workspace inside a second workspace shell. Set `loading` on `FormBuilder` while submitting and `disabled` when required experiment or input state is absent. `readonly` and `size` (`sm`, `md`, `lg`) also apply to the whole form.

`initialValues` in the model overrides the control defaults. Control definitions use `default`. Values loaded from an experiment override both. Do not reapply defaults on each render or replace values after a failed load.

Control options: `type`, `label`, `default`, `placeholder`, `hint`, `required`, `min`, `max`, `minLength`, `maxLength`, `pattern`, `email`, `validation`, `condition`, `access`, `options`, `section`, `view`, `order`, `colSpan`, `props`, and `sidebar`. Section options: `label`, `description`, `columns` (1, 2, or 3), `condition`, `access`, `defaultOpen`, and `showToggle`.

A raw `FormSchema` (sections, wizard `steps`, and exact field definitions) is still the type of the `sidebar.forms` entries and the argument of `useFormBuilder()`. `FormBuilder` itself takes only `spec`.

## Field types

| Type | Backed by | Notes |
|------|-----------|-------|
| `text` | `BaseInput` | Single-line text |
| `email`, `password`, `tel`, `url`, `search` | `BaseInput` | Native input semantics |
| `secret` | `SecretInput` | Managed secret-reference editing |
| `textarea` | `BaseInput type="textarea"` | Multi-line text |
| `number` | `NumberInput` | Numeric with min/max/step |
| `checkbox` | `BaseCheckbox` | Boolean checkbox |
| `toggle` | `BaseCheckbox type="switch"` | Boolean switch |
| `select` | `BaseSelect` | Single choice from `options` |
| `multiselect` | `BaseSelect multiple` | Multiple choices |
| `radio` | `BaseRadioGroup` | Compact single choice |
| `slider` | `BaseSlider` | Range-style numeric input |
| `tags` | `TagsInput` | Free-text tags |
| `date` | `DatePicker` | ISO date string |
| `datetime` | `DatePicker type="datetime"` | ISO timestamp |
| `time` | `DatePicker type="time"` | `HH:MM` string |
| `formula` | `FormulaInput` | Chemical formula with parsing |
| `sequence` | `SequenceInput` | DNA / protein sequence input |
| `molecule` | `MoleculeInput` | Molecule structure input |
| `concentration` | `ConcentrationInput` | Value + unit picker |
| `unit` | `NumberInput` with `units` | Value + unit picker |
| `file` | `FileUploader` | Single or multi-file |
| `path` | `GeneratedPathInput` | Server path reference from a read-only mount |

The canonical list is `FormFieldType` in `packages/sdk-frontend/src/types/form-builder.ts`. The internal registry is readable through `getFieldRegistryEntry(type)` from `@morscherlab/mint-sdk/runtime`.

## Typed tags

Raw `FormFieldSchema` entries (not control definitions) with `type: 'tags'` can set
`itemType: 'number'` to parse entered tags as numbers; `itemType: 'string'` keeps
strings. Generated job forms preserve numeric array defaults and constraints. Keep the
backend's Pydantic model authoritative for submitted input validation.

## Validation

Validation rules attach to each control:

```ts
const spec = defineControlModel({
  controls: {
    name: { type: 'text', label: 'Name', required: true, minLength: 3, maxLength: 200 },
    doi: {
      type: 'text',
      label: 'DOI',
      pattern: { value: '^10\\.\\d{4,9}/.+$', message: 'Must look like 10.NNNN/...' },
    },
    replicates: { type: 'number', label: 'Replicates', required: true, min: 1, max: 12 },
  },
})
```

A `validation` object (`FieldValidation`) works as well. Errors render below each field automatically. Use a template ref when you need imperative validation:

```vue
<script setup lang="ts">
import { ref } from 'vue'
import { FormBuilder } from '@morscherlab/mint-sdk'

const formRef = ref<InstanceType<typeof FormBuilder> | null>(null)

function submit() {
  if (!formRef.value?.validate()) return
  // safe to submit
}
</script>

<template>
  <FormBuilder ref="formRef" :spec="spec" v-model="data" @submit="submit" />
</template>
```

`FormBuilder` exposes `form`, `builder`, `validate()`, `reset()`, `updateSchema()`, `goNext()`, `goBack()`, and `goToStep()`.

For custom rules, set TypeScript-only `enhancements` in the control model:

```ts
const spec = defineControlModel({
  controls: { name: { type: 'text', label: 'Name' } },
  enhancements: {
    fields: {
      name: {
        validate: (value: unknown) =>
          value === 'untitled' ? 'Choose a descriptive name' : null,
      },
    },
  },
})
```

`enhancements` also takes `onSubmit`, `transform`, and `onFieldChange`, and each field takes `visible`, `options`, and `props` callbacks for dynamic behavior. Keep Pydantic validation on the backend as well; browser validation does not protect an endpoint from malformed requests.

## Access-aware controls

Use nested `access` rules on controls/sections and other SDK access-aware UI definitions:

```ts
const controls = {
  batch_limit: {
    type: 'number',
    label: 'Batch limit',
    default: 100,
    access: { permissions: ['plugins.configure'] },
  },
}
```

Access rules live in the nested `access` field. These rules control visibility, not server authorization. Settings endpoints must still require the corresponding backend permission.

## Conditional fields

Controls and sections can declare `condition` to render only when other fields meet a condition:

```ts
{
  subcategory: {
    type: 'select',
    label: 'Subcategory',
    condition: { field: 'category', eq: 'tox' },
  },
}
```

More complex conditions use `and`, `or`, and `not`:

```ts
{
  sections: {
    advanced: {
      label: 'Advanced',
      condition: {
        or: [
          { field: 'expert_mode', eq: true },
          { and: [
            { field: 'category', eq: 'eff' },
            { field: 'replicates', gt: 6 },
          ]},
        ],
      },
      controls: { /* ... */ },
    },
  },
}
```

Available operators: `eq`, `neq`, `gt`, `lt`, `gte`, `lte`, `in`, `notIn`, `truthy`, `falsy`, `contains`, `and`, `or`, `not`.

## Programmatic control with `useFormBuilder`

For pages that need to drive the form imperatively (custom validation step, multi-step wizards), `useFormBuilder` takes a raw `FormSchema` (`@morscherlab/mint-sdk/runtime`):

```ts
import { useFormBuilder } from '@morscherlab/mint-sdk/runtime'
import type { FormSchema } from '@morscherlab/mint-sdk/types'

const schema: FormSchema = {
  sections: [
    { id: 'main', title: 'Main', fields: [{ name: 'replicates', type: 'number', label: 'Replicates' }] },
  ],
}
const builder = useFormBuilder(schema, { replicates: 3 })

async function submit() {
  if (!builder.validate()) return
  await client.savePanel({ body: builder.form.data })
  builder.reset()
}
```

The composable returns `form.data`, `form.errors`, visibility helpers, wizard navigation helpers, and `validate()` / `reset()` / `updateSchema()` methods. The third argument takes `enhancements`.

## Custom rendering

The registry is not a public mutable API. To render a field with custom UI, use the `field:<name>` slot and keep the field in the model so validation, visibility, and submission still work. `section:<id>` replaces a section body, `section:<id>:after` adds content after a section, and `actions` replaces the default action bar:

```vue
<FormBuilder :spec="spec" v-model="data">
  <template #field:dose="{ form }">
    <MyDosePicker
      :model-value="form.data.dose"
      @update:model-value="form.setFieldValue('dose', $event)"
    />
  </template>
</FormBuilder>
```

## Default values

Each control can declare a `default`. When the model is initialized empty, defaults populate. To override the defaults from existing experiment data, bind the loaded values with `v-model`:

```ts
const data = ref(existingDesignData ?? {})
```

Initial data overrides the control defaults. This is intentional for editing flows. With `useFormBuilder`, pass the data as the second argument and read it from `builder.form.data`.

## Saving back to the experiment

The SDK has no composable that writes design data. For experiment-design plugins, submit the form to a plugin endpoint through the generated client. The backend saves with `context.design.save()`:

```ts
import { useExperiment } from '@morscherlab/mint-sdk'
import { useClient } from './generated/mint-plugin'

const experiment = useExperiment()
const client = useClient()

async function handleSave(data: Record<string, unknown>) {
  const id = experiment.id.value
  if (id === null) return
  await client.saveDesign({ pathParams: { experimentId: id }, body: data })
}
```

For a complete page that loads data when picker selection changes and handles missing or failed loads, see [Platform integration](/sdk/frontend/platform-integration#select-load-edit-and-save-an-experiment). This save path requires a platform experiment and permission to write design data. A plugin that declares `Metadata.design` gets every write validated against its schema. For plugin-owned SQL tables, submit through your generated plugin client in the same way.

## Notes

- A raw `FormSchema` is JSON-serializable — you can fetch it from your plugin's backend at runtime and use it with `useFormBuilder`, or in `sidebar.forms`, if it varies per experiment type or per tenant.
- Control models are best for code-owned plugin UI.
- `FormBuilder` syncs external `v-model` changes back into its internal state, so shared values stay coherent when `AppSidebar`, `SettingsModal`, and the main form edit the same object.
- For very large models (50+ fields), split the controls into smaller `sections` or `views` so only the relevant fields are visible at once.
- `multiselect`, `molecule`, and `concentration` fields can hold non-trivial state. Keep them in their own sections so re-renders are scoped.
- For wizards, prefer the `StepWizard` component wrapping multiple smaller `FormBuilder` instances over one giant model.
